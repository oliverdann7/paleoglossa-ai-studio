## 4. OfflineService Architecture

`src/lib/services/offlineService.ts` provides:

- **OfflineText list** — localStorage (`paleoglossa_offline_texts`, keys: index)
- **OfflineTextPayload** — localStorage (`paleoglossa_offline_payloads`, keys: textId-based)
- **SyncQueue** — localStorage (`paleoglossa_sync_queue`, FIFO array)

Used by `Reader.tsx` to:
- Check for offline payload when text fetch fails (line 67)
- Save current text for offline reading (line 779 trigger)
- Remove text from offline store (line 783)

### Limitations

| Issue | Impact |
|-------|--------|
| **localStorage size cap (~5 MB)** | Large texts with full token arrays will hit quota. No IndexedDB fallback. |
| **No Background Sync integration** | The `SyncQueueItem` interface exists but no `sync` event listener in `sw.js` processes it. Queued writes are never flushed. |
| **Payload structure is custom** | Uses `ImportedToken`-like format (flat `type: 'word'`) instead of the curated `Token` format (strict morphology). Reader expects both. |
| **No compression** | Text payloads stored as raw JSON. A 100 KB text expands to ~500 KB in localStorage. |

## 5. Firebase Offline Persistence

**Status: NOT CONFIGURED.**

`src/lib/firebase.ts` initializes Firestore with no offline persistence:

```typescript
const app = initializeApp(firebaseConfig);
export const db = getFirestore(app, firestoreDatabaseId || '(default)');
```

Missing calls:
- `enableIndexedDbPersistence(db)` — enables local cache for Firestore data
- `enableMultiTabIndexedDbPersistence(db)` — same, but works across browser tabs
- `CACHE_SIZE_UNLIMITED` — prevents cache eviction for large vocabularies

### What Firebase offline persistence would give

| Data | Firestore offline | Current behavior |
|------|-------------------|------------------|
| Vocabulary (word states) | ✅ Available read/write, synced on reconnect | ❌ Fails when offline |
| User settings | ✅ Available read | ❌ Fails when offline |
| Imported texts | ✅ Available read | ❌ Fails when offline |
| Reading progress | ✅ Available read/write | ❌ Fails when offline |

### Risks of enabling

- **Cache size**: Default Firestore cache is ~40 MB. For users with 10,000+ vocab items, reading progress across hundreds of texts, and imported texts, this could be tight. Should configure `cacheSizeBytes: 100_000_000` (100 MB).
- **Conflict resolution**: Firestore's offline cache uses last-write-wins for concurrent edits. For vocabulary, this is acceptable (word state is a single value). For notes/settings, also acceptable.

## 6. Reader Offline Requirements

Current `ReadingPane` expects:
- `sentences: SentenceData[]` with `SentenceData.tokens: TokenData[]`
- Each `TokenData` has `{ id, text, lemma, gloss, translit, type, punctBefore, punctAfter, morphology? }`

The `OfflineService` payload format:
```typescript
interface OfflineTextPayload {
  textId: string;
  title: string;
  languageId: string;
  sentences: {
    tokens: { text, lemma, gloss?, type, transliteration?, pos?, confidence? }[];
    translation?: string | null;
  }[];
  source: 'corpus' | 'import';
}
```

**Gap**: The offline payload stores a flat `type` field (e.g., `'word'`) instead of `morphology: Morphology`. The reader's `TokenData` expects either a `morphology` object or a `type` string. If `morphology` is not present, the token renders without POS information. This means offline texts lose all morphological data.

## 7. What Can Be Cached Safely

| Resource | Cache strategy | Notes |
|----------|---------------|-------|
| Static JS/CSS assets | Already precached | Workbox handles this |
| Font files | Already cached (CacheFirst, 1 year) | Google Fonts + Gstatic |
| App shell (`index.html`) | Already precached | SPA navigation handled |
| Language registry data | `CacheFirst` | Static data, rarely changes |
| Dictionary entries (lemma lookup) | `StaleWhileRevalidate` with 1-day TTL | Dictionary data changes slowly; serve cache first, update in background |
| AI explanations | `CacheFirst` with 7-day TTL | AI responses are deterministic per (language, word, lemma) tuple |
| User vocabulary | Firestore offline persistence | Native Firestore cache handles this |
| Reader texts (curated + imported) | `CacheFirst` with manual refresh | Reader texts rarely change; user can manually refresh |

## 8. What Should NOT Be Cached

| Resource | Why |
|----------|-----|
| Authentication tokens | Security — never cache Firebase ID tokens; re-authenticate on each session |
| User API keys | Security — never cache sensitive credentials |
| Live AI usage quotas | Should always be fresh to prevent accidental overuse |
| Stripe subscription status | Should always be fresh to prevent showing stale plan access |
| Real-time tutor messages | Should be NetworkOnly — stale chat history is misleading |

## 10. Deploy & Update Strategy

### Current
- `registerType: 'autoUpdate'` — service worker updates as soon as a new version is detected.
- `skipWaiting()` is called immediately — the new SW activates without waiting for tab closure.
- `clientsClaim()` is adopted — the new SW controls all open clients.
- No update notification UI — users are not informed when the app updates.

### Risk
`autoUpdate` + `skipWaiting()` means users can be halfway through reading a chapter when the page reloads unexpectedly. The `ErrorBoundary` component handles chunk-load errors (auto-retry once), but a mid-reading refresh would lose scroll position.

### Recommendation
Switch to `registerType: 'prompt'` and add an update notification toast:
```
"New version available. Refresh to update."
[Refresh] [Dismiss]
```
